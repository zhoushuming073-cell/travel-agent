# Smart Travel 后端如何生成行程

本文依据 2026-09-07 的当前源码整理，不代表所有外部服务始终可用。入口是 `worker/index.ts` → `worker/travel-api.ts`；算法集中在 `worker/domain/`，模型草案归一化与时间线修复位于 `worker/planning/planner-normalization.ts`。

## 1. 总体机制

这是“外部取证 + 确定性约束优化 + LLM 高层决策与解释”的混合系统，不是把用户一句话直接交给模型生成最终网页，也不是宣称全局最优的数学规划求解器。模型失败时，时间窗插入与局部搜索仍可生成结构化恢复方案。

真实执行路径是浏览器调用 `/api/plan/start` 建立任务，再串行调用 `/api/plan/advance` 推进检查点，同时通过 `/api/plan/status` 查看进度。页面的四阶段是展示层分组，后端实际有 17 个阶段。三套方案在后端逐套生成，并非三路模型并发。

| 顺序 | 检查点 | 实际工作 |
| --- | --- | --- |
| 1 | parse_profile | 提取画像、合并文本硬约束、解析城市 |
| 2 | collect_sources | 执行 preparePlanKnowledge，获取基础资料、实体核验、评分、趋势、人流预测和交通矩阵 |
| 3 | build_knowledge | 保存已生成知识包的阶段摘要，不重新采集 |
| 4 | build_matrix | 保存已有矩阵的核验/估算统计，不重新建图 |
| 5 | planner_research | 缺口识别、搜索计划、取证、证据融合 |
| 6 | planner_memo | 用户开启深度思考时，生成共享决策备忘录 |
| 7—9 | variant_hot / variant_niche / variant_relax | 依次生成经典、自然摄影、轻松避峰草案 |
| 10 | critic_review | 必去覆盖修复后进行独立 AI 审查 |
| 11 | audit_initial | 绑定交通事实、校正时间轴、确定性审计 |
| 12—13 | repair_round_1 / audit_round_1 | 有硬冲突的方案做第一轮 AI 修复，再审计 |
| 14—15 | repair_round_2 / audit_final | 第二轮定向修复、最终安全修复与审计 |
| 16 | final_transit | 调用 buildPlan：实际交通复核、重新排时、费用与可信度计算、结果装配 |
| 17 | compile_result | 最终数据合同校验、持久化结果、标记 done |

代码还保留 `generatePlannerDraft` 等整段编排逻辑，但当前 `/travel` 主要使用 `runPlannerWorkflowStage` 的检查点路径，不能把两者误说成同时执行。

## 2. 任务、并发与恢复

`start` 检查单次 1—7 天限制、会话、幂等键、同会话活动任务、全站并发和每日额度。任务及输入写入 D1，恢复期限是 24 小时。

每次推进只执行下一个未完成阶段。阶段通过 owner + nonce 获取 45 秒租约，每 15 秒续租；写入检查点前确认任务未取消、租约仍属于自己。阶段结果、事件、provider attempts 都持久化。

模型请求新增跨 Worker 的原子调用闸门：同 endpoint + API key 的所有用途共用间隔，数据库只存散列标识，不存明文 key。`AI_REQUEST_MIN_INTERVAL_MS` 默认 65000 毫秒，是保守设置，不是已测得的服务商 QPM。不同部署或本地与生产使用不同数据库时，闸门不互通，因此仍应错开测试。

HTTP 429 最多在同一个请求内尝试 3 次，冷却写入 D1；等待中每至多 5 秒检查取消状态。若仍限流，阶段保存独立的 rate-limit 计数，70 秒后重试，不增加结构错误计数；连续 3 个限流阶段尝试后明确报 `AI_RATE_LIMITED`，保留检查点。用户主动恢复任务时重置对应重试计数。

永久 404/鉴权失败可以直接走透明恢复；其他草案错误先做阶段重试。没有通过校验的结果不能伪装成功。当前限流队列不是严格 FIFO；保守节流会增加总耗时，不能保证跨部署共享账号的配额。

## 3. 画像提取

`deterministicProfileHints` 先读取文本中的城市、日期、人数、预算、天数与必去项；`extractProfile` 再请求结构化模型。中国时区的当天日期用于解析“明天”“8月25日”等表述。

合并顺序强调用户原文中的明确约束优先于表单默认值；未提供的信息保留 Unknown，不应凭空补充。只支持一次一个明确城市或区县。缺少关键目的地时返回 needs_input，不继续规划。

局部重规划已有完整城市、日期、天数、人数时复用结构化画像，并合并之前的必去项，避免重复调用提取模型。

## 4. 候选池与基础事实

天气、景点、住宿并行查询，通过 settled 结果分别标记成功或失败，一个来源失败不会抹掉其他来源。天气失败保持 unavailable；酒店无价格保持未知，不生成假价格。

景点来自 Wikimedia、高德、OSM 等实际 provider。必去点独立核验并实体消歧；做稳定 ID 去重、父子景区处理、坐标合法性检查、排除项匹配、非旅游 POI 过滤与明确关闭状态过滤。必去点随后重新并入候选集合，不因低分直接删除。

候选评分 `scoreSpot`：

```text
必去项得分 = 100，并且排序时另有必去优先级
普通候选得分 = round(0.42×偏好 + 0.20×POI质量
                     + 0.16×数据完整度 + 0.12×时令适配 + 0.10×拥挤适配)
```

偏好匹配使用结构化 Preference Vector 与用户权重。兴趣命中强度为 `min(1, 0.65 + 0.12×命中词数)`；有兴趣时基础分 `35 + 65×加权命中/总权重`，再扣回避项和高拥挤敏感惩罚。没有兴趣时使用中性 50，不把未提及兴趣默认为偏爱。每个分项同时保留 confidence。

数据完整度从 45 分起，来源链接 +15、坐标 +20、简介 +12、开放时间 +8，上限 100。地图评分先按评价量做 Bayesian shrinkage，再映射为 POI 质量；低样本高分不会直接压过大量评价的候选。没有时令证据时使用中性 50 且 confidence=0，不产生正负贡献，也不升级为已核验事实。

## 5. 交通矩阵

候选池与交通图容量已经解耦。必去项始终进入 active graph，普通候选按评分补足，当前 active graph 的常规目标上限为 48 个候选；必去项超过该数时不会因固定上限被截断。

OSRM Table 返回道路距离和驾车时间，但系统只保留住宿边、必去相关边和每个节点的 KNN 边，形成 `hotel-required-knn-lazy` 稀疏图。公共交通偏好时不能把驾车分钟数直接当公交时间，而是用距离模型估算，再按必去数量和行程天数选择 3—10 条高风险边做规划前高德公交核验。每条边同时携带 expected、p80、p95、min 与 confidence；轻松方案使用更保守的 p80。OSRM 不可用时仍生成明确标记为 estimated 的稀疏后备图。

选定行程的相邻两点若不在这张稀疏图里，编译器会按两点坐标补一条明确标记 `estimated` 的候选边，并为它预留交通时间；坐标缺失时仍保留硬错误，不能编造路线。最终交通阶段继续对行程实际相邻边做地图核验。不能再把“稀疏图原本未存这条边”误报成必须经两轮 AI 修复的硬冲突。

给模型的紧凑知识包保留住宿/必去相关边及各点最近邻，最多 120 条。缺失边由优化器基于透明坐标距离估算，最终行程选定后再核验实际相邻边，跨三方案复用相同交通请求。

## 6. Research Agent：按决策价值取证

研究对象是必去优先的高价值候选，同时保留一部分高潜力、高不确定 reserve；普通模式目标 10 个、深度模式目标 15 个，全部必去项永不因该目标数被截断，内部安全上限可扩到 24 个候选。对每个景点列出开放、临时关闭、预约、票价、交通变化、时段、人流等缺口。用户有预算时票价缺口会进入研究。

缺口效用：

```text
U = 决策影响 × 不确定性 × 预期信息增益 × 时效需求
    × (1 + 0.5×反事实目标提升) / max(0.15, 研究成本)
```

各因子在代码中限界；时效需求最低按 0.25 参与效用。阻断行程的缺口先于普通缺口，再按 U 降序。查询选择会计算目标、事实类型与文本相似度；非阻断查询相关性过高时跳过，避免重复取证。

研究复杂度：

```text
C = 0.15×天数 + 0.75×额外城市数 + 0.35×必去数量
  + 0.25×阻断未知数 + 0.20×高风险事实数 + 0.03×候选数
  + 0.30×动态事件数 + 0.40×跨城段数
```

普通/深度查询硬上限分别为 32/56；目标查询数为 `ceil((4+1.5C)×模式系数)`，模式系数为 1/1.5，并受上限约束。页面目标约为查询目标的 1.25 倍。AI 次数预算也由复杂度计算，不等同于最终实际调用次数。

实际循环普通最多 2 轮、深度最多 3 轮：

1. 第一轮 AI 只提出搜索计划，不直接宣布事实；模型不可用且非持续限流时，可用确定性查询计划。
2. 约束 targetId 和问题类型必须来自缺口；相同目标/问题/查询去重，并对同目标同事实的近似查询施加相关性惩罚。第一轮最多 8 条，其后每轮最多 5 条，所以实际查询还受更紧的轮数上限约束。
3. 模型只在第一轮提出研究查询策略；后续轮次根据更新后的缺口与证据使用确定性查询规划。没有阻断性缺口、上一轮决策信息增益低于 0.04 且剩余最高研究效用低于 0.2 时提前停止，保留高风险/阻断事实的继续取证能力。
4. 搜索及页面抓取各以并发 3 运行。Search Orchestrator 按问题选择来源；搜索、页面、事实按不同 TTL 缓存，namespace 带 `FACT_POLICY_VERSION`，指定日期事实不会污染长期事实缓存。
5. 页面文本作为不可信外部证据，清理注入指令，识别读取失败、登录限制、摘要等访问状态。仅有 snippet 不能验证关键事实。
6. 规则提取候选证据，AI 可辅助从已读取原文提取字段；结果必须能被原文支撑。
7. 证据打分、去重、融合成事实；更新缺口状态和实际信息增益，再决定是否继续。

证据得分：

```text
S = 0.25×实体匹配 + 0.20×相关性 + 0.15×来源适配
  + 0.15×权威性 + 0.15×新鲜度 + 0.10×具体性
  - 0.18×商业偏向 - 0.22×SEO风险
```

实体匹配低于 0.55、相关性低于 0.45、失效来源或页面不可用可直接拒绝；S<0.5 拒绝，S≥0.72 且页面证据允许才接受，否则 weak。

转载、同内容或同独立性组只保留一个最强证据。同值证据累加权重；冲突事实根据优势证据组与差距计算 0.35—0.72 的置信度，不再固定封顶 0.55。无冲突且读取到官方原文为 verified；否则置信度≥0.68 为 supported，其余 inferred。

实际信息增益为新解决缺口的决策影响增量/总决策影响。连续两轮增益<0.04 停止；无阻断项且最高 U<0.08 可停止。预算耗尽、没有新查询或达到轮数也停止。仍有阻断项且本轮信息增益≥0.12 时，可以在硬上限内扩展预算。

## 7. 人流预测不是实时人数

`predictCrowdRisk` 是可解释规则模型，不是训练后的客流预测网络。基础 26 分，加日期、景点类型、天气、公开趋势、社交提及、地图评分等修正，截断到 0—100。新结果同时区分 `crowdIntensity`、`crowdUncertainty` 和结合置信度的 `crowdImpact`。

例如热门地标 +13；大尺度户外 -5；部分入口受限类型 +8。预报降雨概率≥60% 时，室内替代需求 +8，户外 -8，半户外 -4。不同类型有不同分时修正，最后按实际到访日期和时刻重新计算。

公开可比日期样本可有限校准基础分，最大影响权重 0.34。评分映射为较少/一般/较多/拥挤/非常拥挤，并输出置信度、证据覆盖和区间。规范字段为 `crowdRiskScore`（0—100 风险分，不是统计概率）；`riskProbability` 仅为旧持久化方案和旧前端读取保留的 deprecated 兼容别名，任何界面与新算法都不得把它解释为概率；`officialRealtime` 始终 false。

## 8. 三方案与 AI 审查

深度模式先请求简短共享决策备忘录；随后依次为三目标请求短策略骨架：

- hot：代表性与必去覆盖，减少跨区。
- niche：自然、摄影、时令和光线，有天气风险时用候选池内替代。
- relax：更少节点、更多缓冲、低拥挤风险与公共交通。

模型只能从合法候选 ID 中输出标题、策略、候选 ID 与 day theme，不再决定精确分钟。后端优化器根据完整事实、时间窗、交通与目标 preset 生成每一天的可执行时间轴。旧版完整 days/daysPlan/itinerary 容器仍可在 repair 边界归一化，但不是主规划路径。

`aiJson` 先严格解析 JSON；语法失败最多再做一次只修语法/容器的模型调用，不允许新增事实。当前生产路由使用 DeepSeek 官方 API：需求提取与用户画像固定走 `deepseek-v4-flash`，研究、增强、规划、critic、修复和解释固定走 `deepseek-v4-pro`。`AI_STRICT_MODEL_ROUTING=true` 时不会跨职责静默回退；模型是否可调用仍取决于账号授权，不能把 UI 标题当实际返回模型。

请求显式发送 `thinking: {type: "enabled" | "disabled"}`，同时保留 `chat_template_kwargs.enable_thinking` 兼容字段。参数依据 [DeepSeek 官方接口说明](https://api-docs.deepseek.com/guides/thinking_mode/)；必须根据真实输出、错误码与结构校验验收，不能仅因配置字段存在就宣称模型正常。

确定性审计先处理结构问题；只有偏好违背、体验重复、风格不一致等语义问题存在时才调用 Structured Critic。它只能输出 target/type/severity/evidenceRef/proposedAction/confidence/message，AI 的 hard 意见仍降为 warning。

## 9. 硬约束编译与修复

先补齐必去绑定，再把完整矩阵事实绑定到相邻点，按实际交通时间顺延时间线，然后审计：三方案数量、天数、必去覆盖、候选池合法 ID、重复景点、活动重叠、开放时间、每日起止、午餐、晚餐、餐饮地标饭点、夜景日落时间和返回时间。

午餐开始须在 11:00—13:30；行程延续到 18:00 后须有 17:00—20:00 开始的晚餐。相邻景点之间须留足矩阵交通时间。夜景以当日日落为下界，缺日落数据时有明确代码默认值，并非日落实测。

方案差异用景点集合 Jaccard 与顺序差异检查：最大 Jaccard>0.9 且最小顺序差异<0.35 时判差异不足。

修复顺序是：必去覆盖 → 交通绑定 → 时间线合法化 → 饭点与安全修复 → 同日/跨日局部搜索 → 移除低价值 optional → 仅在仍有硬冲突时调用 AI semantic repair。最终交通变长后允许一次 deterministic micro-repair；必去项不能为凑时间删除。不可行预检返回 violations 与 minimalConflictSet，最终仍有硬冲突则报错。

## 10. 模型不可用时的确定性恢复

`recoverPlannerVariant` 调用 `optimizeRouteBuckets`。这是带时间窗的启发式优化器，不是精确 TSP、整数规划、强化学习或全局最优保证。

选点时必去是硬约束，模型 seed 只作为高层偏好。hot/niche/relax 使用不同目标权重，并加入 uncertainty、天气、票价、效用密度、切换成本、体验连续性和前序方案相似度；时令未知不获得中性先验红利。轻松方案的节点密度、p80 交通、疲劳与缓冲惩罚更保守。

算法先放必去、窄时间窗、预约与夜景节点，再做 time-window insertion；随后执行 2-opt、同日/跨日 relocate、swap 和 8 轮确定性 LNS（定向移除 15%—25% 风险/低效节点后重插）。核心时间以分钟整数计算；游览时长使用 min/expected/max 区间，景区入口退出缓冲、饭点资源、天气适配、连续活动和跨日疲劳都进入可行性与目标函数。

`plannerScore`、`scoreBreakdown`、各分项 confidence、约束、uncertainty、availability windows 和来源从候选检索一直保留到 optimizer、repair 与最终 candidatePool，不再在 `preparePlanKnowledge` 丢失。

## 11. 最终交通、费用、风险与合同

`buildPlan` 将草案转换为每日 attraction / leg / rest 块，核验真实相邻交通并重新排时；再查询餐饮，按实际到访时段更新人流预测。

Trip Cost V2 确定性汇总住宿、票价、餐饮、市内交通、已识别城际段及风险缓冲，输出 min/expected/max。费用风险按金额和证据质量加权，预算判断关注 max 风险边界；票价也进入路线目标。酒店候选额外计算位置、评分和参考价的透明 utility，但未核验房态/成交价仍保持 Unknown。

费用缓冲基础权重：verified 3%、referenced 7%、estimated 15%；按金额暴露加权，每个未知项追加风险，上限受显式规则约束。存在主要未知费用时汇总标记 partial，不能显示误导性的充足剩余预算。

`analyzePlanTrustV2` 依次生成事实状态、证据图、未知项排序、最低核验清单、依赖图、关键路径、缓冲、编译评分、脆弱性与情景模拟。可信度计算为：

```text
可靠度 = clamp(round(0.36×方案评估 + 0.24×信息完整度 + 0.20×约束分
                  + 0.12×min(100,最小缓冲分钟×2) + 0.08×图覆盖 - 结构惩罚))
```

这不是模型自报分数，也不是统计意义的旅行成功率。除六类可解释情景测试外，系统以稳定 seed 执行 400 次 Monte Carlo，输出准时率、硬约束成功率、p50/p90 延迟和预计删除 optional 数；它只用于方案稳健性比较，不是现实事件概率承诺。

最终 Contract 3.0 还要求 planner/scoring/crowd/cost 版本、统一 Fact Graph、Monte Carlo、Reproducibility snapshot 和 POI/类别/区域/时段/节奏五维 Diversity。相同请求可用 profile、candidate、fact、provider hash、模型、prompt、optimizer 和 seed 回放定位差异。

## 12. 当前边界

- 研究不是无限联网，既受预算也受每轮查询数和最大轮数限制。
- 预算参与提示词和研究，但最终超预算目前主要给出警告；不能描述成严格预算可行性求解。
- 启发式优化与 Monte Carlo 不构成全局最优或现实成功率保证；精确校准仍需要未来真实用户反馈数据。
- 入口坐标没有可靠来源时使用明确标记的 POI centroid fallback；不会伪称已核验入口。大型景区增加透明 entry/exit buffer，但精细内部路线仍取决于可用证据。
- 17 个 D1 checkpoint 为现有恢复和 UI 兼容合同；内部另提供依赖 DAG 元数据，尚未把持久化状态机改造成并行调度器。
- 模型名、页面“进行中”、动画标题和后台调用成功是不同事实，必须分别验证。
- 本地与生产 D1 不共用配额闸门；使用同账号时仍应错峰。429 或 404 的账号授权/额度问题无法仅靠本地代码保证消失。
- 模型恢复成功不代表天气、预约、酒店价格、交通全部已核验。最终仍可能因其他真实数据缺口标记降级。
