# Smart Travel 后端如何生成行程

本文依据 2026-09-05 的当前源码整理，不代表所有外部服务始终可用。入口是 `worker/index.ts` → `worker/travel-api.ts`；算法集中在 `worker/domain/`，模型草案归一化与时间线修复位于 `worker/planning/planner-normalization.ts`。

## 1. 总体机制

这是“外部取证 + 多次 LLM 决策 + 确定性约束编译”的混合系统，不是把用户一句话直接交给模型生成最终网页，也不是一个求全局最优解的数学规划求解器。

真实执行路径是浏览器调用 `/api/plan/start` 建立任务，再串行调用 `/api/plan/advance` 推进检查点，同时通过 `/api/plan/status` 查看进度。页面的四阶段是展示层分组，后端实际有 17 个阶段。三套方案在后端逐套生成，并非三路模型并发。

| 顺序 | 检查点 | 实际工作 |
| --- | --- | --- |
| 1 | parse_profile | 提取画像、合并文本硬约束、解析城市 |
| 2 | collect_sources | 执行 preparePlanKnowledge，获取基础资料、实体核验、评分、趋势、人流预测和交通矩阵 |
| 3 | build_knowledge | 保存已生成知识包的阶段摘要，不重新采集 |
| 4 | build_matrix | 保存已有矩阵的核验/估算统计，不重新建图 |
| 5 | planner_research | 缺口识别、搜索计划、取证、证据融合 |
| 6 | planner_memo | 用户开启深度思考时，生成共享决策备忘录 |
| 7—9 | variant_hot / variant_niche / variant_relax | 依次生成经典、自然摄影、轻松避峰草案 |
| 10 | critic_review | 必去覆盖修复后进行独立 AI 审查 |
| 11 | audit_initial | 绑定交通事实、校正时间轴、确定性审计 |
| 12—13 | repair_round_1 / audit_round_1 | 有硬冲突的方案做第一轮 AI 修复，再审计 |
| 14—15 | repair_round_2 / audit_final | 第二轮定向修复、最终安全修复与审计 |
| 16 | final_transit | 调用 buildPlan：实际交通复核、重新排时、费用与可信度计算、结果装配 |
| 17 | compile_result | 最终数据合同校验、持久化结果、标记 done |

代码还保留 `generatePlannerDraft` 等整段编排逻辑，但当前 `/travel` 主要使用 `runPlannerWorkflowStage` 的检查点路径，不能把两者误说成同时执行。

## 2. 任务、并发与恢复

`start` 检查单次 1—7 天限制、会话、幂等键、同会话活动任务、全站并发和每日额度。任务及输入写入 D1，恢复期限是 24 小时。

每次推进只执行下一个未完成阶段。阶段通过 owner + nonce 获取 45 秒租约，每 15 秒续租；写入检查点前确认任务未取消、租约仍属于自己。阶段结果、事件、provider attempts 都持久化。

模型请求新增跨 Worker 的原子调用闸门：同 endpoint + API key 的所有用途共用间隔，数据库只存散列标识，不存明文 key。`AI_REQUEST_MIN_INTERVAL_MS` 默认 65000 毫秒，是保守设置，不是已测得的服务商 QPM。不同部署或本地与生产使用不同数据库时，闸门不互通，因此仍应错开测试。

HTTP 429 最多在同一个请求内尝试 3 次，冷却写入 D1；等待中每至多 5 秒检查取消状态。若仍限流，阶段保存独立的 rate-limit 计数，70 秒后重试，不增加结构错误计数；连续 3 个限流阶段尝试后明确报 `AI_RATE_LIMITED`，保留检查点。用户主动恢复任务时重置对应重试计数。

永久 404/鉴权失败可以直接走透明恢复；其他草案错误先做阶段重试。没有通过校验的结果不能伪装成功。当前限流队列不是严格 FIFO；保守节流会增加总耗时，不能保证跨部署共享账号的配额。

## 3. 画像提取

`deterministicProfileHints` 先读取文本中的城市、日期、人数、预算、天数与必去项；`extractProfile` 再请求结构化模型。中国时区的当天日期用于解析“明天”“8月25日”等表述。

合并顺序强调用户原文中的明确约束优先于表单默认值；未提供的信息保留 Unknown，不应凭空补充。只支持一次一个明确城市或区县。缺少关键目的地时返回 needs_input，不继续规划。

局部重规划已有完整城市、日期、天数、人数时复用结构化画像，并合并之前的必去项，避免重复调用提取模型。

## 4. 候选池与基础事实

天气、景点、住宿并行查询，通过 settled 结果分别标记成功或失败，一个来源失败不会抹掉其他来源。天气失败保持 unavailable；酒店无价格保持未知，不生成假价格。

景点来自 Wikimedia、高德、OSM 等实际 provider。必去点独立核验并实体消歧；做稳定 ID 去重、父子景区处理、坐标合法性检查、排除项匹配、非旅游 POI 过滤与明确关闭状态过滤。必去点随后重新并入候选集合，不因低分直接删除。

候选评分 `scoreSpot`：

```text
必去项得分 = 100，并且排序时另有必去优先级
普通候选得分 = round(0.42×偏好 + 0.20×POI质量
                     + 0.16×数据完整度 + 0.12×时令适配 + 0.10×拥挤适配)
```

偏好匹配使用中文兴趣词表与用户权重。兴趣命中强度为 `min(1, 0.65 + 0.12×命中词数)`；有兴趣时基础分 `35 + 65×加权命中/总权重`，再扣回避项和高拥挤敏感惩罚。没有兴趣时基础分为 60。

数据完整度从 45 分起，来源链接 +15、坐标 +20、简介 +12、开放时间 +8，上限 100。POI 质量由评分或静态质量类别分档映射。没有时令数据使用中性 50 分，只用于排序，不升级为已核验事实。

## 5. 交通矩阵

选择最多 18 个景点，必去优先，加住宿锚点形成最多 19 个节点。全有向矩阵最多 `19×18=342` 条边。

OSRM Table 返回道路距离和驾车时间。公共交通偏好时不能把驾车分钟数直接当公交时间，而是用距离模型估算，再选与住宿/必去项相关及近邻的高价值边，最多 6 条做规划前高德公交核验。OSRM 不可用时使用带 estimated 标记的后备矩阵。

给模型的紧凑知识包保留住宿/必去相关边及各点最近邻，最多 120 条；完整矩阵仍用于编译器校验。最终行程选定后，再核验实际相邻边，跨三方案复用相同交通请求。

## 6. Research Agent：按决策价值取证

研究对象是必去优先的高价值候选：普通模式最多 10 个，深度模式最多 15 个。对每个景点列出开放、临时关闭、预约、票价、交通变化、时段、人流等缺口。用户有预算时票价缺口会进入研究。

缺口效用：

```text
U = 决策影响 × 不确定性 × 预期信息增益 × 时效需求 / max(0.15, 研究成本)
```

各因子在代码中限界；时效需求最低按 0.25 参与效用。阻断行程的缺口先于普通缺口，再按 U 降序。

研究复杂度：

```text
C = 0.15×天数 + 0.75×额外城市数 + 0.35×必去数量
  + 0.25×阻断未知数 + 0.20×高风险事实数 + 0.03×候选数
  + 0.30×动态事件数 + 0.40×跨城段数
```

普通/深度查询硬上限分别为 32/56；目标查询数为 `ceil((4+1.5C)×模式系数)`，模式系数为 1/1.5，并受上限约束。页面目标约为查询目标的 1.25 倍。AI 次数预算也由复杂度计算，不等同于最终实际调用次数。

实际循环普通最多 2 轮、深度最多 3 轮：

1. AI 只提出搜索计划，不直接宣布事实；模型不可用且非持续限流时，可用确定性查询计划。
2. 约束 targetId 和问题类型必须来自缺口；相同目标/问题/查询去重。第一轮最多 8 条，其后每轮最多 5 条，所以实际查询还受更紧的轮数上限约束。
3. 搜索及页面抓取各以并发 3 运行。Search Orchestrator 按问题选择来源；搜索、页面、事实按问题类型分别缓存。
4. 页面文本作为不可信外部证据，清理注入指令，识别读取失败、登录限制、摘要等访问状态。仅有 snippet 不能验证关键事实。
5. 规则提取候选证据，AI 可辅助从已读取原文提取字段；结果必须能被原文支撑。
6. 证据打分、去重、融合成事实；更新缺口状态和实际信息增益，再决定是否继续。

证据得分：

```text
S = 0.25×实体匹配 + 0.20×相关性 + 0.15×来源适配
  + 0.15×权威性 + 0.15×新鲜度 + 0.10×具体性
  - 0.18×商业偏向 - 0.22×SEO风险
```

实体匹配低于 0.55、相关性低于 0.45、失效来源或页面不可用可直接拒绝；S<0.5 拒绝，S≥0.72 且页面证据允许才接受，否则 weak。

转载、同内容或同独立性组只保留一个最强证据。同值证据累加权重；第二组权重达到 `max(0.65, 第一组×0.72)` 时保留 conflicting，置信度封顶 0.55。无冲突且读取到官方原文为 verified；否则置信度≥0.68 为 supported，其余 inferred。

实际信息增益为新解决缺口的决策影响增量/总决策影响。连续两轮增益<0.04 停止；无阻断项且最高 U<0.08 可停止。预算耗尽、没有新查询或达到轮数也停止。仍有阻断项且本轮信息增益≥0.12 时，可以在硬上限内扩展预算。

## 7. 人流预测不是实时人数

`predictCrowdRisk` 是可解释规则模型，不是训练后的客流预测网络。基础 26 分，加日期、景点类型、天气、公开趋势、社交提及、地图评分等修正，截断到 0—100。

例如热门地标 +13；大尺度户外 -5；部分入口受限类型 +8。预报降雨概率≥60% 时，室内替代需求 +8，户外 -8，半户外 -4。不同类型有不同分时修正，最后按实际到访日期和时刻重新计算。

公开可比日期样本可有限校准基础分，最大影响权重 0.34。评分映射为较少/一般/较多/拥挤/非常拥挤，并输出置信度、证据覆盖和区间。字段 `riskProbability` 当前直接沿用 0—100 的风险分，它不是经过历史样本概率校准的真实发生概率；`officialRealtime` 始终 false。

## 8. 三方案与 AI 审查

深度模式先请求简短共享决策备忘录；随后依次请求：

- hot：代表性与必去覆盖，减少跨区。
- niche：自然、摄影、时令和光线，有天气风险时用候选池内替代。
- relax：更少节点、更多缓冲、低拥挤风险与公共交通。

模型输入包含画像、紧凑知识包、研究事实及未知项、当前目标、已有方案摘要和要求的 JSON 结构。每套必须返回全部日期。后端兼容 days/daysPlan/itinerary、activities/items 等容器，但不能把缺失日期认定为已生成。

`aiJson` 先严格解析 JSON；语法失败最多再做一次只修语法/容器的模型调用，不允许新增事实。用途路由的模型名是候选配置，是否可调用仍取决于账号授权；不能把 UI 标题当实际返回模型。

请求现在显式发送 `thinking: {type: "enabled" | "disabled"}`，同时保留原有 `chat_template_kwargs.enable_thinking` 兼容字段。前者来自 [DeepSeek 官方接口说明](https://api-docs.deepseek.com/guides/thinking_mode/)，元景是第三方兼容服务，参数被接受不等于已证明其执行效果完全相同。必须根据真实输出、错误码与结构校验验收，不能仅因配置字段存在就宣称模型正常。

独立 Critic 阅读三套草案、研究事实和确定性问题，输出审查意见。AI 的 hard 意见在汇入编译记录时降为 warning，真正阻止输出的是确定性审计的硬错误，不是模型未经验证的自评。

## 9. 硬约束编译与修复

先补齐必去绑定，再把完整矩阵事实绑定到相邻点，按实际交通时间顺延时间线，然后审计：三方案数量、天数、必去覆盖、候选池合法 ID、重复景点、活动重叠、开放时间、每日起止、午餐、晚餐、餐饮地标饭点、夜景日落时间和返回时间。

午餐开始须在 11:00—13:30；行程延续到 18:00 后须有 17:00—20:00 开始的晚餐。相邻景点之间须留足矩阵交通时间。夜景以当日日落为下界，缺日落数据时有明确代码默认值，并非日落实测。

方案差异用景点集合 Jaccard 与顺序差异检查：最大 Jaccard>0.9 且最小顺序差异<0.35 时判差异不足。

每轮只向存在硬冲突的方案发修复请求，最多两轮。最终安全编译可补午晚餐、重排交通、移除非必选超时节点；必去项不能为凑时间随意删除。最终仍有硬冲突则报错，不返回“可靠完成”。

## 10. 模型不可用时的确定性恢复

`recoverPlannerVariant` 调用 `optimizeRouteBuckets`。这是贪心启发式，不是精确 TSP、整数规划、强化学习或全局最优搜索。

选点时必去优先分 10000、模型已有 seed 优先分 2000；非必去且与之前方案重复扣 11。三目标分别组合偏好、热门、质量、完整度、时令、拥挤分；未知字段每项扣 2.5。轻松路线默认每天 2 点，其他路线慢节奏 3 点、常规 4 点；容量至少容纳所有必去项。

分天时对每个待分配景点计算：`接近该日已有点的最小交通分钟 + 该日已选点数×平衡系数`，选择代价最低的日期。平衡系数 relax=18，其余=11。日内从必去/高经典分节点出发，最近邻贪心排序，识别出的夜景点后移。之后套入饭点、游览时长和休息骨架，再经过相同硬约束审计。

实现细节限制：初始 `scoreSpot` 确实影响候选排序，但 `preparePlanKnowledge` 当前构造的 plannerSpots 没有显式携带 plannerScore/scoreBreakdown。恢复优化器对这些字段可能使用默认偏好50、质量60、完整度45；不能声称恢复阶段完整使用了前一轮所有评分分项。本文只记录此问题，未顺手改变选点逻辑。

## 11. 最终交通、费用、风险与合同

`buildPlan` 将草案转换为每日 attraction / leg / rest 块，核验真实相邻交通并重新排时；再查询餐饮，按实际到访时段更新人流预测。

Trip Cost V1 确定性汇总住宿、票价、餐饮、市内交通、已识别城际段及风险缓冲，输出 min/expected/max。公交按人数，出租车按共享规则；门票依据研究证据，房价区分参考价和指定日期核验价。未识别金额不以 0 冒充。

费用缓冲基础权重：verified 3%、referenced 7%、estimated 15%；按已计价项目数量平均，每个未知项另加 2%，上限 28%。存在主要未知费用时汇总标记 partial，不能显示误导性的充足剩余预算。

`analyzePlanTrustV2` 依次生成事实状态、证据图、未知项排序、最低核验清单、依赖图、关键路径、缓冲、编译评分、脆弱性与情景模拟。可信度计算为：

```text
可靠度 = clamp(round(0.36×方案评估 + 0.24×信息完整度 + 0.20×约束分
                  + 0.12×min(100,最小缓冲分钟×2) + 0.08×图覆盖 - 结构惩罚))
```

这不是模型自报分数，也不是统计意义的旅行成功率。情景测试分别模拟晚出发45分钟、排队60分钟、交通30分钟、遇雨35分钟、关闭75分钟、体力下降40分钟；沿依赖图传播，扣除缓冲，给出抗扰动/可修复/脆弱判断，不伪称实际预测。

最终结果包含 request、alternatives、research、planner、进度与比较信息。每套含 daysPlan、budgetBreakdown、planningDecision、事实/证据/风险等。`assertPlanContract` 校验稳定 hot/niche/relax、天数、必去项、时间与数据性质，结果持久化后任务才标记 done。

## 12. 当前边界

- 研究不是无限联网，既受预算也受每轮查询数和最大轮数限制。
- 预算参与提示词和研究，但最终超预算目前主要给出警告；不能描述成严格预算可行性求解。
- 候选矩阵最多18个景点，大量必去项可能超过容量并导致后续校验拒绝。
- 模型名、页面“进行中”、动画标题和后台调用成功是不同事实，必须分别验证。
- 本地与生产 D1 不共用配额闸门；使用同账号时仍应错峰。429 或 404 的账号授权/额度问题无法仅靠本地代码保证消失。
- 模型恢复成功不代表天气、预约、酒店价格、交通全部已核验。最终仍可能因其他真实数据缺口标记降级。
